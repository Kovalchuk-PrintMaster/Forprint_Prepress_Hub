# Живе ТЗ: каталог, версії, право на зміну

## Мета
Глобальний каталог вимог із **одним відповідальним джерелом** на вимогу. Пропонується логічна ієрархія: Goal Contract → Product Blueprint / Workflows → Roadmap/Microsteps → Evidence/Progress → Architecture/Knowledge Registry. Це пов'язані записи, а не обов'язково чотири фізичні «рівні»; їх треба звірити з чинним Blueprint governance.

## READY_FOR_IMPLEMENTATION
Можна починати крок, якщо: (1) затверджена кінцева мета/обмеження; (2) задекларовані входи і виходи; (3) відомий спосіб приймання; (4) блокувальні невизначеності для цього кроку вирішені; (5) виконавець здатний почати без домислювання результату. `OPEN_NONBLOCKING` допускається. Цільові зміни — тільки за окремим людським рішенням.

## Версії та workflow
Незмінний `workflow_id` для однакової семантики; `version` для правил; `run_id` для окремого запуску. Новий незалежний функціональний варіант — новий профіль/workflow, а не перезапис чинного. Старі версії залишити придатними для історичного відтворення. Дублікат → `RETIRE_CANDIDATE`, але не видаляти без доказів і permission.

## Переоцінка після змін
За кожної суттєвої вимоги: (a) impact graph повного roadmap; (b) конфлікти; (c) зайві/deduplicated кроки; (d) зміна acceptance; (e) незалежні гілки; (f) потреба операторської санкції; (g) оновлення Assistant Context Pack. Тільки зачеплені кроки `BLOCKED/REASSESSMENT_REQUIRED`.

## Каталог та пошук (пропозиція)
Логічні поля: spec_id, goal_id, module_owner, version, lifecycle, acceptance_ref, depends_on, capabilities, reusable_tool_refs, implementation_refs, evidence_refs, supersedes, timestamps. Для пошуку — текстовий індекс за семантикою і машинні метадані. Не створювати паралельний реєстр замість наявного System Blueprint без меж ownership.

## Невідомі деталі
Серверний canonical каталог, його owner і точний шлях ще НЕ узгоджено з реальними репозиторіями. Пропозиція цієї теки — лише candidate для review. Асистент не має права сам призначити собі роль операційного реєстру всього ForPrint.
